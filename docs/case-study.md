# Lawyer Case Copilot 产品 Case Study

## 1. 问题定义

案件负责律师面对的不是一个孤立法律问题，而是一组持续变化的材料、事实、证据、人员、程序节点和专业判断。普通法律问答无法保存案件上下文，也难以说明结论来自哪份材料、是否经过律师确认。

本项目因此把产品单位定义为“案件工作空间”，而不是“聊天会话”。

## 2. 目标用户与任务

| 用户 | 核心任务 |
|---|---|
| 案件负责律师 | 快速形成案件全貌、发现证据缺口、控制风险并作出最终判断 |
| 律师助理 | 整理材料、核实事实、维护时间线和准备工作底稿 |
| 协作团队 | 在同一案件上下文中查看进度、来源和复核记录 |

## 3. 产品决策

### 为什么不是法律聊天机器人

- 案件处理需要长期状态，而不是单轮答案；
- 事实必须绑定文件、页码和原文；
- 材料冲突不能被模型自动“消解”；
- 高风险内容需要明确进入律师复核队列；
- 同一基础能力需要适配不同案件类型。

### 为什么采用编排工作流

系统使用一个 Workflow Orchestrator 串联结构化节点。节点负责材料处理、事实提取、时间线、领域路由、证据矩阵、风险、任务和报告，各节点有明确输入、输出、状态和来源。

不采用多个互相对话的 Agent，原因是：

- 节点责任更容易测试；
- 执行过程更容易回放；
- 失败可以局部重跑；
- 避免对话式 Agent 放大幻觉和成本；
- 更符合律所对可追溯性和可控性的要求。

### 为什么采用领域插件

通用案件共享材料、事实、时间线、证据和复核能力；交通事故人伤案件再加载专业分类、治疗过程、医疗费用、鉴定、赔偿项目与完整性规则。这样可以在不复制通用流程的前提下继续扩展合同、劳动等领域。

## 4. 核心工作流

```text
案件创建
→ 材料解析与分类
→ 事实和时间线
→ Domain Router
→ 通用分析 / 交通事故人伤专业模块
→ 证据与缺失材料
→ 风险和争议
→ 律师人工复核
→ 辅助报告
```

## 5. 信任与安全设计

系统严格区分：

1. 原始材料；
2. AI 提取事实；
3. AI 推理建议；
4. 知识检索结果；
5. 律师确认结论。

每条当前事实保存来源引用和复核状态。材料中的指令被视为不可信数据；没有材料依据的模型输出不会进入当前事实；责任、因果关系、伤残等级、证据效力和法律适用始终由律师判断。

## 6. 评测方法

仓库包含 2 个完全虚构案例和 6 个结构化回归场景，验证：

- 事实来源覆盖；
- 材料缺失识别；
- 信息冲突识别；
- 赔偿项目矩阵完整性；
- 强制人工复核；
- 无来源模型输出拦截。

这些指标只说明系统处理完整性，不代表真实案件准确率、法律正确率或业务效果。

## 7. 关键取舍

| 选择 | 原因 |
|---|---|
| 模块化单体 | MVP 易理解、易运行，避免框架复杂度 |
| Mock Provider 默认启用 | 面试演示稳定，不需要密钥 |
| SQLite 默认存储 | 降低本地启动成本，可迁移 PostgreSQL |
| 规则使用 YAML | 便于律师补充经验、版本化和回归测试 |
| 不生成最终法律文书 | 避免把辅助系统包装为自动法律判断 |
| 完全虚构 Demo | 防止泄露真实客户和案件信息 |

## 8. 下一阶段

优先由项目所有者补充经过脱敏和核验的交通事故办案经验，并建立律师标注评测集。登录、多租户、对象存储和生产部署属于企业化能力，不作为当前作品集叙事的中心。
